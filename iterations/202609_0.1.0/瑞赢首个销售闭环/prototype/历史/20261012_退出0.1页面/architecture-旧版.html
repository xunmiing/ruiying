一、系统定位与边界

依据：assets/system-overview.md §1、§3

瑞赢是公司自建的销售 CRM，以唯一客户主档为底座，管理客户、联系人、线索、商机、销售活动、任务、日程、日报、知识及销售管理过程。 客户关系网以集团关系、总分关系、上游、下游四类轻量关系表达客户之间的关联；客户＋区域＋业务线经营关系表达经营责任和资格；全国公海是零条有效经营关系的客户主档池。 销售 Agent 在权限范围内生成候选，经人工确认形成正式事实。

瑞赢同时承担两类职责：（1）管理签约前销售过程，包括线索、商机、销售活动、任务、日报和管理反馈； （2）维护「这个客户主体是谁」的公司级唯一客户主档——客户身份不会因业务线、负责人或下游系统不同而重复建立。

依据：assets/system-overview.md §1 系统定位。

瑞赢负责（§3.1）
  • 客户主档及轻量客户关系网。
  • 公司级客户价值分级直接设置并留日志，以及客户—区域—业务线责任关系。
  • 联系人及联系人—客户关系。
  • 线索、线索池、分派、主动认领、跟进、转换和拆分追溯。
  • 商机、商机业务线明细、销售场景、流程模板、阶段推进、关闭结果和拆分追溯。
  • 销售活动、独立正式拜访、任务、统一日历投影、日报、轻量知识、消息及管理反馈。
  • 统一客户销售活动、销售活动／正式拜访原件引用及集团聚合时间线；0.1 不建设独立原件治理。
  • 销售 Agent 候选提炼、人工确认、来源追溯和操作审计。
  • PC 销售过程管理分析和数据质量视图。
  • 纷享销客现用线索数据的迁移与替换。
瑞赢不负责（§3.2）
  • 不把下游业务系统的「上海易鑫（车电业务）」「上海易鑫（车务业务）」等业务记录复制成新的客户主体。
  • 不在首个验证版本接入合同、订单、履约、应收、回款、成本和报销等复杂下游业务。
  • 不把 AI 推断直接作为正式客户、线索、商机、销售活动、任务或报告事实。
  • 不在未明确授权和人工确认时自动报价、承诺、对外发送或执行高风险写入。
  • 不以采购工作手机作为首个版本启动前提。
  • 不在瑞赢中重建公司知识库的复杂文件审批和版本系统；0.1 的瑞赢轻量知识文档与公司级知识事实源明确分层。

签约、订单、履约、应收、回款和成本等交易及经营事实仍由对应业务系统负责；这些系统通过稳定客户标识关联瑞赢客户主档，不在瑞赢中再建立另一套客户主体事实（§1）。

核心产品原则要点（§7，共 31 条，此处只摘录与架构直接相关的部分）
  • 客户主体唯一；对象独立、关系连接；业务线与客户身份分离。
  • AI 先生成候选——Agent 输出默认经销售查看、修改和确认后才进入正式业务数据。
  • 权限不被 AI 绕过——Agent 继承当前用户权限，读取、写入和对外发送分别控制。
  • 自动能力可降级——Agent 或企微输入不可用时，销售仍可手工完成核心业务流程。
  • 统一 H5 执行、PC 治理——销售和主管共用一个企微 H5 业务工作台；PC 承担数据维护、配置发布、治理、审计和深度分析。
  • 后续关系先验证、后建设——股权、控制、商业合作和资方只有在真实业务流程验证必要后才进入正式版本，不提前建立空表、隐藏菜单、状态或自动化规则。

依据：assets/system-overview.md §7 核心产品原则第 1、2、3、6、8、9、15、31 条。

二、两个统一入口与端职责

依据：prd/00 §1.1、§1.2；system-overview.md §1
企微 H5：index.html
  • 企业微信 H5 是销售与主管的高频执行端，继续承接日常查看、记录、跟进、确认和闭环。
  • 对 Agent 而言，H5 是 0.1 主操作端；Agent 在 H5 完整提供：AI 首页、沟通整理、候选确认、AI 待确认（当前／历史待处理／写入失败）、会议任务确认、对象 AI、日报和主管关注。
  • 「零额外入口」：销售与主管主要在企业微信 H5 完成高频执行。
  • 销售和主管共用一个企微 H5 业务工作台，菜单按角色能力和数据范围展示。
统一 PC 应用：pc.html
  • PC 采用「一个统一应用 + 一个工作区 + 一个首页 + 五个一级导航分组」。
  • 五个一级导航为：客户管理、销售管理、工作管理、分析、系统管理。
  • 所有人工用户登录后统一进入首页；业务页面、分析页面、治理页面和配置页面只是同一导航体系中的不同功能分组，不形成新的权限层级。
  • PC 只提供 AI 数量／状态入口、团队处理情况、既有日报、运行记录、能力配置和试点范围，不建设 PC 自由输入和完整候选编辑器；AI 运行记录和失败治理归 05／08；06 只提供一个 Agent 配置页面（能力、来源、试点范围、预生成四个页签）。
  • PC 承担数据维护、配置发布、治理、审计和深度分析。
跨端一致性
  • 两端共用同一套候选、权限、状态和正式写入结果（system-overview.md §1）。
  • PC 与 H5 共用业务对象 ID、业务状态、权限和数据范围、版本控制及正式业务事实；业务深链不经过首页，直接打开目标页面并重新鉴权（prd/00 §1.2）。
  • PC 修改后不要求 H5 实时推送，H5 刷新或重新进入时读取最新事实（prd/00 §9）。
H5 明确不建设的能力
  • 不建设管理看板（团队分析看板）、指标趋势和指标下钻——只保留 04 的团队任务、团队日报、拜访复核等高频源业务入口。
  • 不提供通用批量编辑；批量操作仅统一 PC 应用中具备对应动作权限的用户可使用。H5 无导出和个人保存视图。
  • 不建设 PC 自由输入和完整候选编辑器；PC 的 Agent 配置页不得拆成四个一级页面。

依据：prd/00 §1.1、§1.2、§11；prd/06 §2（「H5 不建设团队分析看板、趋势和指标下钻」「Agent 四项是同一页面页签」）； prd.md §3.4（批量操作仅统一 PC 应用）；prd.md §6.3（H5 无导出和个人保存视图）；system-functional-modules.md §2（入口与工作台行「H5 不建设管理分析、趋势和指标下钻」）。

四、核心业务闭环

依据：assets/system-overview.md §5
客户价值／客户关系网／区域业务线经营责任／线索／商机／销售活动信息
→ 自建、主管指派、沟通提炼或规则生成候选／正式任务
→ 候选经人工确认写入正式任务，正式任务直接待处理
→ 负责人提交成果后直接完成，逾期仅作时间标记
→ 形成销售活动、客户反馈和下一步
→ Agent 提炼候选销售活动和候选任务；日报使用独立版本模型
→ 销售查看、修改和确认
→ 正式记录回写瑞赢
→ 日报和管理分析按权限汇总已确认事实
→ 主管反馈形成后续任务或跟进要求

依据：assets/system-overview.md §5 核心业务闭环原文。约束：日报不能成为脱离业务记录的二次填报；管理分析不能直接统计未经确认的 AI 推断（§5）。

首个版本必须形成的端到端能力（system-functional-modules.md §3）
客户价值、区域业务线责任、客户关系网／线索信息进入
→ 分派或主动认领
→ 形成候选或正式任务并按需接收
→ 销售执行并记录销售活动
→ 线索转换或按商机流程模板推进
→ Agent 生成候选销售活动和候选任务
→ 发起人确认候选／日报独立编辑并一次提交
→ 成果型任务按需验收，普通任务直接完成
→ 正式记录和任务回流
→ 主管看板查看并反馈

依据：assets/system-functional-modules.md §3。首个版本可以降低单个模块的功能深度，但不能删掉任务、日报、Agent 或看板而破坏闭环。

六、业务对象模型要点

依据：assets/business-object-model.md
一句话模型（§1）

瑞赢用唯一客户主档表达「现实中的客户主体是谁」，用客户关系网表达客户间的业务或组织关联，用公司级价值档案表达人工价值判断， 用客户—区域—业务线经营关系表达责任和销售经营资格，用客户级全国公海记录表达零条有效经营关系的待分配状态， 用联系人关系表达「谁与哪些客户有关」，用当前地址和业务地址快照区分当前地点与历史事实。 线索、商机、销售活动、任务、日程和日报继续按各自生命周期独立建模。

七、对象状态机要点

依据：assets/state-machine.md（状态名一律取自文档）
对象状态关键约束
线索 待处理、跟进中、已转化、无效 是否在线索池、当前持有人及保护期与业务状态分开管理；进入跟进中必须同时保存正式销售活动、下一步动作和下次跟进日期；跟进中不能回到待处理；已转化为终态，无效误判仅能由主管或纠错权限人员撤销

客户经营关系与公海 存在有效经营关系 / 全国公海 全国公海只包含零条有效经营关系的客户主档，同一客户最多一条有效公海记录，且与有效经营关系互斥；公海不保留待分配的当前区域或业务线；认领或分派时才指定区域、业务线和主负责人，原子创建初始经营关系，并发仅一人成功

Agent 写入执行 未写入 → 写入中 → 写入成功 / 写入失败 写入失败可按原幂等键重试并重新校验；候选决策与写入执行分开
正式任务 待处理、已完成、已取消 所有正式任务创建后直接待处理；负责人完成后直接已完成，创建人可改期或取消；阶段上下文失效时由系统取消并留存原因。逾期由截止时间实时计算，不覆盖主状态。
正式拜访 计划中 → 进行中 → 已完成；计划中 → 已取消；计划中 → 未到访；进行中 → 已取消 异常记录为「待复核 → 已复核」或「待复核 → 待补充 → 待复核」；异常不自动改变拜访主状态；销售活动修订和拜访补充以追加版本或纠错记录实现，不回退销售活动、拜访、任务或日报状态
日报 草稿 → 已提交 对销售只保留一次提交操作，提交后不再发生内容状态流转；AI 首次原始底稿、当前草稿和销售提交版本分别保存；提交前动态刷新正式事实，提交时冻结正文、事实快照和来源；主管打开正文详情才自动已读，建议只追加
独立日程 有效 → 已取消 / 已删除；已取消 → 已删除 只有独立日程维护日程主状态，任务、拜访、线索和商机在日历中为源对象投影；独立日程转任务以派生字段记录，不增加「已转换」主状态；企微同步只覆盖独立日程和正式拜访
人员移交 待预检 → 待确认 → 处理中 → 部分成功 / 已完成；待预检／待确认 → 已取消 人员离岗移交使用独立处理单记录进度，不修改源对象自身的业务状态；人员停用不等待移交完成；H5 只展示移交／代办待处理摘要、状态和处理编号，不推进本状态机

八、权限模型

依据：assets/permission-model.md
角色（§1）
角色定位主要能力
R1 销售一线业务人员处理本人及被授权协作范围内的客户、线索、商机、活动、拜访、任务、日程和日报
R2 销售主管团队管理者在授权团队范围内进行分派、验收、复核、日报建议和管理分析
R3 销售运营业务运营与配置维护维护获授权的业务配置、指标、知识和数据质量能力
R4 客户数据管理能力包客户资料维护能力包按权限直接维护客户主体、客户关系网、合并与恢复；修改即时生效并写入历史
R5 系统管理员系统固定最高权限人工角色拥有全部页面、业务动作、数据范围、字段查看、配置、原件及系统管理能力
R6 Agent / 服务身份非人工登录身份在调用用户权限与服务身份权限交集内执行获准动作

多角色用户的有效权限直接取并集，不设置主角色。R4 是能力包，不是独立工作区（§1）。 R5 默认无条件拥有全部 PC/H5 页面权限、业务动作权限、数据范围、字段查看权限、配置管理权限、原件查看／下载／处置权限和全部系统管理能力；只有 R5 可以授予或撤销其他用户的 R5，系统必须始终保留至少 1 个有效 R5（§2）。

权限计算公式（§3）
角色页面权限 ∩ 动作权限 ∩ 数据范围 ∩ 字段规则 ∩ 当前对象状态
  • 普通多角色取各角色授权并集后，再执行对象状态、字段安全和业务规则校验。
  • 页面菜单不是新的权限层级，只是已有页面权限的导航表现。
  • 搜索、列表、详情、导出、分析下钻均沿用同一页面权限和数据范围（§4）。
每次进入重新鉴权（§3）
  • 首页快捷入口；全局搜索结果；消息、深链和复制链接；列表进入详情；关联对象跳转；H5/PC 跨端进入；下载与重试。
  • 失权后不得继续展示对象标题、摘要、数量或无权关联关系。
管理分析与业务配置能力项（§4.1）

分析能力：查看管理分析 / 查看指标下钻 / 查看敏感字段明文 / 导出指标明细

配置能力：查看配置 / 编辑配置（含校验）/ 发布配置 / 启用／停用配置

  • 汇总、下钻、明文和导出分别计算；配置查看、编辑、发布和启停分别计算。
  • 角色是默认权限集合，能力项是服务端最终授权依据；除 R5 固定最高权限模型外，不得根据角色名称直接推断用户拥有某项 06 权限，尤其不能默认 R3 拥有全部配置能力。
  • 下载导出文件时重新校验创建人、当前导出能力、对象数据范围和字段权限；已失权时禁止领取。
人员变化与权限收敛（§5）
  • 公司用户中心是组织、人员及销售准入资格的事实源；瑞赢自动同步合格人员并授予基础 R1。
  • 变化影响当前权限时：立即停止受影响的旧权限范围 → 保留未变化的权限范围 → 生成权限待处理事项和受影响业务对象清单 → 不自动授予新范围 → 不自动完成业务移交。
  • 恢复资格只恢复人员有效状态和基础 R1，不自动恢复历史额外角色、数据范围或业务责任。
  • 0.1 不建设临时代办或临时待办委托。
原件、知识与 Agent（§6）与安全降级（§7）
  • 原件依附销售活动或正式拜访，按当前业务对象权限查看和下载；普通用户不能替换或删除已经成为正式业务证据的原件，R5 可查看、下载和处置。
  • 知识仅对已发布且处于当前用户发布范围内的用户可见；知识链接不扩大权限，打开时重新鉴权。
  • R6 只能使用当前正式已发布、调用用户有权访问的知识版本；执行动作时调用用户权限与服务身份权限取交集，并记录操作来源。
  • 谁发起 Agent 提炼，谁确认候选；主管只查看团队候选处理统计和本来有权的业务正文，不能代销售确认。
  • 候选未确认前撤权时，不再展示无权原文，候选失效且不允许继续确认；正式写入后完全回归原业务模块权限。
  • R5 的正式 CRM 最高权限不自动转化为 AI 运维对来源原文的查看权。
  • 权限或身份服务异常时不得默认放大权限；短时异常可使用有有效期的最近一次有效权限缓存，没有有效缓存或缓存失效时拒绝访问。

依据：assets/permission-model.md §1～§7。技术评审待定项见该文件 §8（权限缓存有效期与实现方式、高并发撤权传播时延、字段级规则的技术表达方式、R6 服务身份的凭证轮换与最小授权实现）。

九、Agent 边界

依据：system-overview.md §1.1、§9；permission-model.md §6
Agent 最终边界（system-overview.md §1.1）
  • Agent 不建立第二套 CRM；外部材料、AI 推断和未确认候选均不是正式业务事实。
  • 所有正式业务写入必须人工确认，服务端重新鉴权、校验和幂等后调用正式业务接口。
  • 系统主动预生成仅包含今日预计处理任务总结、主管关注摘要和日报底稿；不主动推送。
  • 工作手机自动采集不进入 0.1。一期使用 Coze 私有化承担生成与编排，瑞赢保留鉴权、候选、确认、写入、幂等和审计控制。
Agent 与任务、日报、看板的关系（system-overview.md §9）
  • 用户界面展示自建任务、主管指派、沟通提炼和规则生成四类来源；候选确认和阶段生成作生成路径追溯。
  • Agent 可以从获授权输入和瑞赢正式数据中生成候选销售活动、候选任务、日报独立底稿和提示；候选至少保留来源版本、字段证据、事实／推断／缺失、确认方式和写入结果。
  • Agent 展示拟写字段、来源证据和查重结果；人工修改确认后调用对象正式创建流程。0.1 先试点少数能力，后续按同一架构扩展。
  • 会议纪要只生成候选，支持人工批量确认；知识检索结果不自动创建任务。
  • 正式任务只有待处理、已完成、已取消；逾期是时间标识。创建人可按权限调整截止时间并留痕。
  • 看板统计范围受数据权限控制并只使用正式事实；0.1 不提供个人排行榜或自动绩效结论。
不做自由对话式问答、不构成第二个 CRM 的边界表述
  • 瑞赢 Agent 核心为「沟通内容 → 对象匹配 → 候选销售活动＋候选任务 → 人工确认 → 正式写入」；日报不进入通用候选；不直接建客户／联系人／线索／商机；不自动建任务、排优先级或裁决冲突（system-functional-modules.md §2 瑞赢 Agent 行）。
  • 对象 AI 为权限内知识检索，只读摘要与问答，不改写正式字段（prd/00 §1.1 与页面清单 PG-AI-OBJECT 契约视图）。
  • Coze 负责模型、Prompt、Agent／Workflow、知识检索流程和 AI 工具编排；瑞赢负责 H5／PC 交互、用户鉴权、数据权限、上下文、候选、人工确认、正式写入、幂等、重试、审计、能力开关、试点范围、来源配置和预生成调度；Coze 不得绕过瑞赢候选与人工确认直接写 CRM（integration-boundaries.md §7.1）。
  • Agent 失败、超时或输入不可用时转为手工录入；系统不能因 Agent 不可用阻断核心销售流程（state-machine.md §5）。

依据：assets/system-overview.md §1.1、§9；assets/system-functional-modules.md §2；assets/integration-boundaries.md §7.1；assets/state-machine.md §5。

十、集成边界、外部依赖、失败降级与人工接管

依据：integration-boundaries.md；system-overview.md §10
总原则（integration-boundaries.md §1）
  • 瑞赢内部正式业务事实由 01～07 已确认的业务对象、状态与规则定义；第二阶段治理能力只服务已有业务事实，不创建第二套 CRM 事实。
  • 外部系统失败不得改变瑞赢内部正式业务状态。
  • 每类集成必须明确事实源、同步方向、白名单字段、幂等标识、失败恢复和审计要求。
  • 外部回调与瑞赢事实冲突时，不允许系统静默任选一方覆盖。
外部系统登记与边界（§2）
  • 0.1 仅登记已经正式接入的系统，维护：系统名称、环境、负责人、服务身份、能力范围、启停状态、最近健康状态。
  • 密钥、Token、密码不得在普通页面或日志中明文展示。
  • 0.1 不建设 API 管理平台、通用接口编排器、用户自定义接口或通用字段 Mapping 平台。
人员与身份（§3）
  • 公司用户中心是组织、人员及销售准入资格的事实源；瑞赢自动消费人员事件并保证重复、乱序事件不会让旧状态覆盖新状态。工号缺失、冲突、格式异常或身份无法唯一匹配时，不创建正式人员，进入「人员同步异常」。
  • 企业微信认证：瑞赢只消费公司既有企微认证结果，不建设绑定、改绑或人工身份映射维护。未绑定、工号不一致、认证失效或认证失败时拒绝登录。
统一同步任务（§4）
  • 状态：待处理 → 处理中 → 成功 / 失败。
  • 至少记录：来源系统、业务对象、方向、外部 ID、幂等标识、状态、执行时间、最后成功时间、失败原因、重试次数。
  • 同步失败先由系统自动重试，次数和间隔由技术方案确定；超过上限后进入失败并创建统一异常事项，R5 可人工重试。人工重试仍须执行幂等和正式业务校验。
  • 0.1 不建设通用对账平台；具体集成确需对账时，仅提供检查差异和重新同步能力。
  • 只有真实存在「瑞赢对象 ↔ 外部对象」映射的集成才允许解除映射；人员同步、身份认证等事实源集成不允许解除映射。
企业微信日程集成（§5）
  • 0.1 只同步独立日程和正式拜访；任务不创建企微日程。
  • 瑞赢业务事实优先；只有白名单字段可以受限双向同步；企微不能修改任务截止时间、正式拜访业务状态或其他未授权业务事实。
  • 企微删除或取消外部日程不能自动取消正式拜访，只更新外部映射和同步状态，必要时提示重新同步。
  • 如企微实际 API 不支持完整双向同步，产品能力必须降级为「瑞赢 → 企微」单向同步，不展示不存在的能力。
消息投递（§6）
  • 站内消息是正式消息记录；企业微信是额外提醒渠道；只有产品白名单重要事件发送企微；用户不能自行配置企微事件。
  • 业务事件发生时计算并保存接收人快照，后续组织或人员变化不得改写历史消息。
  • 投递状态为「待发送 / 发送中 / 成功 / 失败」，阅读状态为「已读 / 未读」，两者完全独立。
  • 投递失败自动重试；超过上限创建「消息投递失败」异常事项，R5 可人工重试；消息失败不得回滚来源业务事务。
  • 0.1 不建设消息静默时段、消息合并窗口、个人消息偏好、通用渠道降级链或通用通知编排平台。
知识与 Agent 输入（§7、§7.2）
  • 只有当前正式已发布且调用用户有权限访问的知识版本可以被 R6 Agent 引用；系统必须能够追溯知识来源、版本、调用用户和服务身份。
  • 文字／粘贴为核心阻断输入；大圆在线文档、录音／语音、图片和文件为 0.1 正式增强输入，按来源开关和 POC 验收。工作手机自动采集不进入本期。
  • 来源版本变化后原候选失效，基于新版本另建候选；多来源相似只提示，冲突证据并列展示并由人工选择。
失败、超时与人工接管（§8）
  • 外部系统不是正式事实源时，其失败不阻断瑞赢可独立完成的核心业务。
  • 高影响写请求必须具有请求唯一标识和幂等能力。

已发现的文档间口径差异（如实报告，不在本页裁定）
  • 页面总数：103（登记表）对 53（prd.md 表述）。 assets/js/page-manifest.js 的 verify() 返回 total = 103（PC 66 + H5 37），而 prd.md §6.0 说明编号段仍写「不计入 53 个页面契约 id」。 两者口径不同：登记表按「端 × 行」计数（同一页面契约 id 在 H5 与 PC 各登记一行），登记表内去重后的契约 id 数亦为不同数值，与 53 均不一致。本页数字一律采用登记表 verify()。
  • prd/00 §3 导航树含「AI 运行记录与失败治理（归 05／08）」子分组，但 §6 系统管理分组表未列出该分组。 页面契约登记表中存在对应条目（pc/ai/ops.html，契约 PG-AI-OPS）。两处不一致。
  • 页数 ≠ prd 能力条目数。 prd/00 §6 以能力条目描述页面（例如知识管理写作「知识列表、知识详情／编辑、发布与停用」），而页面契约登记表按 HTML 页面计数（知识管理为 2 行，发布与停用作为同一页面的视图承载）。 本页的模块页数一律取自登记表行数。
  • rules.md 未设「已删除能力清单」独立章节。 本页第十一节按 rules.md 中实际含「0.1 不建设」表述的编号条目逐条引用，未替文档补写或合并章节。
