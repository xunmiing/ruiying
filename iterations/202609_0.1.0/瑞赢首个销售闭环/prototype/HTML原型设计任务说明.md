# 瑞赢 0.1 HTML 原型设计任务说明

> 版本：V2.1｜日期：2026-09-21｜状态：已按统一入口、业务页面拆分和公共能力共享更新  
> 文档用途：说明如何依据当前 PRD 重建 HTML 原型，包括输入依据、当前范围、页面组织、文件结构、生成顺序和验收要求。  
> 本文不是页面设计稿，不新增业务规则，也不替代 `prd.md`、模块 PRD 或 `testcase.md`。

## 1. 已确认的原型结构决策

瑞赢 0.1 原型不再按“销售端、主管端、配置端”拆成三个彼此独立的产品。最终只保留两个产品入口和一个说明入口：

1. `index.html`：统一企业微信 H5，销售和主管共用；差异由角色权限、数据范围和对象状态决定。
2. `pc.html`：统一 PC 应用，同时承载业务执行、管理分析和系统管理；不同角色看到不同导航、数据和操作。
3. `architecture.html`：架构与评审说明，不承载正式业务操作，不作为页面契约。

产品入口数量不等于业务 HTML 文件数量。`index.html`、`pc.html` 仍是统一产品入口；客户列表、客户详情、客户新增等可独立进入和独立评审的稳定业务页面，分别维护为 HTML。弹窗、抽屉、Tab 和局部操作状态不单独拆 HTML。

最终结构采用：

> **统一入口、业务页面拆分、公共能力共享。**

- HTML：按稳定业务页面拆分。
- 页面专属样式与交互：就近放在对应 HTML 内。
- CSS：只保留跨页面公共样式。
- JavaScript：只保留样例数据、跨页状态、权限、导航、页面清单和公共交互等真正跨页面能力。
- 不再使用 `pc-customer.js`、`pc-lead.js`、`pc-opportunity.js` 等文件承载整个业务页面。

## 2. 本次任务目标

将瑞赢 0.1 已确认的产品设计转化为可浏览、可点击、可用于产品、业务、研发和测试联合评审的高保真业务原型，重点验证：

1. 销售能否在企业微信 H5 完成高频销售执行闭环。
2. 主管能否在同一 H5 内完成团队业务处理，不形成独立主管系统。
3. PC 是否能承担客户、线索、商机等对象的完整查看、复杂操作、批量处理和导入导出。
4. H5 与 PC 是否使用相同对象 ID、状态、权限、数据范围和业务事实。
5. 新增、编辑、关联、转换、批量、导入、导出、失败恢复等操作是否完整。
6. Agent、企微日历及其他外部能力不可用时，核心业务是否仍可手工完成。

原型只表达产品逻辑、信息结构、页面状态和关键交互，不承担生产代码、真实接口、数据库设计或部署方案职责。

## 6. 三个入口的职责

### 6.1 `index.html`：统一企业微信 H5

- 主画布为 430px 企业微信 H5。
- 销售和主管进入同一应用，不使用独立主管端。
- 主管依据角色能力增加团队线索、团队任务、团队日报、验收和复核入口。
- 角色差异必须由权限、数据范围、对象状态和动作能力体现，不能简单替换整套页面。
- 移动端优先处理高频、短路径操作；复杂导入导出、宽表和深度治理转到 PC。
- 本轮不生成尚未确认的主管经营看板和指标下钻。

### 6.2 `pc.html`：统一 PC 应用

- 主画布为 1280px PC 宽屏。
- 采用一个应用、一个工作区、一个首页和统一导航。
- 当前先承载客户、线索、商机等业务对象的完整查看与复杂操作。
- 06 确认后，在同一 PC 入口下增加分析与系统管理业务页面，不建设独立配置中心应用。
- 销售、主管、运营、知识管理员、客户数据管理员和系统管理员按权限看到不同菜单、数据和操作。
- 最高管理员也必须遵守对象状态、字段约束、版本冲突和审计规则。

### 6.3 `architecture.html`：架构与评审说明

- 说明系统边界、端侧职责、对象关系、业务闭环、Agent 可信执行和集成边界。
- 不承担新增、编辑、审批、配置等业务操作。
- 不计入业务页面契约；与 PRD 冲突时以正式 PRD 为准。

## 7. 页面拆分、路径与操作组织

### 7.1 页面拆分判断

满足以下条件之一时，可拆为独立 HTML：

- 是 PRD 登记的稳定页面契约或明确具体视图。
- 需要直接深链进入并可独立评审。
- 具有独立的加载、空、失败、无权限和操作完成状态。
- 表单、步骤或信息结构复杂，放入弹窗会影响完整评审。

以下内容不单独拆 HTML：弹窗、抽屉、Tab、筛选展开区、字段选择器、二次确认、局部状态和简单字段编辑。

以客户为例：

```text
pc/customer/list.html                                  客户列表
pc/customer/create.html                                客户新增与查重
pc/customer/detail.html?id=CUS-001                     客户详情
pc/customer/detail.html?id=CUS-001#contacts            联系人 Tab
pc/customer/detail.html?id=CUS-001#network             客户关系网 Tab
pc/processing/detail.html?id=JOB-001                   导入、导出或批量处理结果
```

客户字段编辑、联系人关联、客户关系网维护和客户价值设置继续放在客户详情的抽屉或弹窗中，不分别创建 HTML。线索、商机、任务等对象采用相同原则；拆分必须与主 PRD 和 00 页面清单对账，不得因为源码方便自行增加业务页面契约。

### 7.2 操作呈现原则

| 操作 | 推荐呈现 |
|---|---|
| 简单字段修改 | 弹窗或侧边抽屉 |
| 字段多、分组多、校验复杂 | 独立新增／编辑页面 |
| 选择或关联其他对象 | 选择抽屉或弹窗；保留检索、权限和无结果状态 |
| 转换、合并等高影响操作 | 独立步骤页或明确确认流程 |
| 导入 | 独立步骤页，包含模板、校验、预检、提交和结果 |
| 导出 | 从列表发起，在统一处理记录中查看状态和下载 |
| 批量操作 | 列表发起，先预检，再确认，最后展示逐条结果 |
| 低频动作 | 收入“更多”，但不能因原型空间不足而删除 |

### 7.3 路径、参数与状态约束

- HTML 相对路径定位稳定业务页面；查询参数传递对象、来源、模式和演示状态；hash 只用于页面内 Tab 或锚点。
- 直接打开任一业务 HTML 必须落到正确页面并重新模拟鉴权，不能要求先经过统一入口。
- 统一支持 PRD 已登记的 `id`、`from`、`state`、`preview`、`drill` 等语义；物理路径变化不得改变参数含义。
- 从详情返回时通过 URL 与 `sessionStorage` 恢复来源页面、Tab、筛选、排序和页码。
- 业务状态、阅读状态、同步状态、处理状态和派生标识分别表达。
- `prototype-store.js` 统一管理演示会话中的跨页数据变化，并提供“重置演示数据”能力。
- H5 与 PC 对同一对象的修改必须回到同一份共享样例事实，不允许互相矛盾；端内页面状态可以分别保存。

## 8. 页面与公共代码职责

### 8.1 共享层

- `demo-data.js`：集中保存初始样例对象和字典，不直接承担跨页持久化。
- `prototype-store.js`：使用 `sessionStorage` 管理跨页演示状态、版本和重置。
- `permissions.js`：角色能力、数据范围、字段权限和操作判断。
- `navigation.js`：生成统一 H5／PC 导航、面包屑、角色评审切换和公共页面外壳。
- `page-manifest.js`：登记业务页面路径、页面契约、端、角色、范围和评审状态，用于覆盖检查。
- `common-actions.js`：弹窗、抽屉、确认、提示、异步处理和错误反馈。

### 8.2 页面专属内容

- 页面专属结构、字段、状态区和操作入口放在对应 HTML。
- 页面专属 CSS 直接放在该 HTML 的 `<style>` 中。
- 页面专属 JavaScript 直接放在该 HTML 的 `<script>` 中。
- 页面只调用公共数据、权限、导航、存储和交互能力，不把业务页面渲染函数放回公共 JS。
- 同一对象的列表、详情和复杂表单可以分别维护，但弹窗、抽屉、Tab 和局部状态留在所属页面。

### 8.3 共享边界

只有至少被两个独立业务页面使用、且语义一致的能力才能进入公共 CSS 或 JS。不得为了减少单页代码而创建 `pc-customer.js`、`pc-lead.js`、`pc-opportunity.js` 等承载整个模块页面的业务脚本。

## 9. 原型生成顺序

### 阶段 1：建立对账清单

1. 从主 PRD §6.0 和 00 页面清单提取当前页面契约、路由、端、角色和优先级。
2. 为每页建立“对象—动作—状态—权限—异常—验收”最小卡片。
3. 标记本轮纳入、06 暂缓和 1.0 后续范围。
4. 对照模块 PRD 与测试用例列出缺失或冲突；不得在原型中猜测。

### 阶段 2：受控重建共享基础

1. 建立统一设计变量、基础组件、页面清单、导航、样例数据、跨页状态和权限模拟。
2. 建立 430px H5 与 1280px PC 两套明确的信息布局，不做简单缩放。
3. 建立加载、空、无权限、失败、成功、冲突和部分成功等公共状态。
4. 保留旧原型作为对照，不直接在旧业务结构上继续叠加补丁。

### 阶段 3：生成统一 H5

优先打通：

```text
今日工作
→ 客户／线索／商机查看
→ 任务或正式拜访执行
→ 销售活动记录
→ Agent 候选人工确认
→ 日报生成与一次提交
→ 主管阅读、标记和追加建议
```

并验证线索转换、独立日程与拜访日程、知识检索、消息深链及外部能力失败后的手工路径。

### 阶段 4：生成 PC 业务执行端

按以下顺序完成：

1. 首页、导航、搜索、消息和处理记录。
2. 客户、联系人和客户关系网。
3. 线索、线索池业务操作和转换结果。
4. 商机、流程阶段、团队和阶段任务。
5. 销售活动、正式拜访、任务、日程和日报。
6. 批量、导入、导出、部分成功、重试和版本冲突。
7. Agent 状态入口和来源追溯。

### 阶段 5：06 确认后的扩展

在同一 `pc.html` 入口下增加 `pc/analysis/`、`pc/admin/` 页面，随后执行一次全导航、全角色和跨端回归。本阶段当前不执行。

### 阶段 6：验证与记录

1. 页面契约、路由和模块逐项对账。
2. 正常、异常、边界、权限和跨端场景与 `testcase.md` 对账。
3. 检查旧术语、旧状态、旧对象和旧页面入口残留。
4. 更新 `CHANGELOG.md`，记录修改依据、实际覆盖、验证结果和未完成范围。

## 10. 视觉与交互原则

### 10.1 企业微信 H5

- 以单手操作、高频任务、短路径和弱网可恢复为优先。
- 详情先展示状态、责任、下一动作和风险，再展示完整字段。
- 复杂筛选使用抽屉，重要结果和失败原因必须可见。
- 不把 PC 表格缩小后当作移动方案。

### 10.2 PC 第二执行端

- 适合完整字段、宽表、组合筛选、批量、导入导出和跨对象查看。
- 复杂操作可使用侧栏、分栏详情和步骤式表单。
- 新增、编辑、关联和批量结果必须形成完整闭环，不能只展示列表和详情。
- PC 与 H5 不建立第二套业务状态或数据事实。

### 10.3 Agent

- 明确区分输入、来源、候选、草稿、人工确认、写入中和正式数据。
- Agent 不直接创建客户、联系人、线索或商机，只能生成未提交表单草稿。
- 销售活动、任务和日报候选经过人工确认后才能成为正式数据。
- 会议候选允许人工批量确认，但每项独立校验并返回结果。
- 知识检索只提供有权内容，不自动创建任务。

## 11. 明确禁止事项

- 不把 9 月 16 日 1.0 全景直接等同于 0.1。
- 不把销售、主管和管理员制作成三个独立产品。
- 不恢复 `manager.html`、`admin.html` 作为新原型正式入口。
- 不按每个按钮或 CRUD 动作机械拆 HTML；弹窗、抽屉、Tab、局部状态和简单编辑不单独成页。
- 不把全部页面代码重新堆进一个超大 HTML。
- 不使用 `pc-customer.js`、`pc-lead.js`、`pc-opportunity.js` 等公共脚本承载完整业务页面。
- 不用 `fetch()` 或 iframe 动态拼装业务页面，不让原型依赖本地服务器才能打开。
- 不新增主 PRD和 00 页面清单未登记的正式业务页面或路由。
- 不根据旧 HTML 按钮反向创造业务规则。
- 不在 06 确认前生成看板、指标和配置治理页面。
- 不让 Agent 绕过人工确认、权限校验或普通表单。
- 不把任务完成自动等同于阶段推进、线索转换或销售活动创建。
- 不把日程或时间线投影复制成第二份业务事实。
- 不增加日报退回、重提或建议自动转任务。
- 不虚构个人企微日程双向同步或企微日程完成状态。
- 不放入真实客户、联系人、手机号、凭证或生产接口地址。
- 不把原型视为生产实现或技术架构承诺。
