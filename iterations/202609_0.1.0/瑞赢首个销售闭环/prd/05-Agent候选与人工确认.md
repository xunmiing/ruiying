# 05 Agent 候选与人工确认模块 PRD

> 本版权限变更：仅销售、销售主管/经理、管理员（运营）三个人工角色；配置功能列表与按钮权限；按固定角色范围查看完整业务信息。HTML 原型本次未更新。

> 版本：V1.0.3｜日期：2026-10-08｜状态：已同步 DEC-063 权限口径，并承接总 PRD 的模块产品细则
> 上位文档：`../prd.md`。Agent 不能绕过权限、候选不等于事实、正式业务写入必须人工确认。  
> 技术底座：一期使用 Coze 私有化部署版；Coze 负责生成，瑞赢负责鉴权、上下文、候选、确认、正式写入、幂等、审计和降级。

0.1 正式任务只有待处理、已完成、已取消；“待确认”只属于 AI 候选。业务可见的 AI 运行记录与失败处理保留在 PC，权限校验、同步重试、投递和审计技术日志由技术人员查看分析并处理，具体规则由技术定义。

## 1. 模块定位与统一链路

05 模块不是自主经营客户的“AI 销售”，而是在瑞赢现有 CRM 对象、状态机、权限和正式业务接口之上增加可信辅助能力，不建立第二套 CRM。

```text
合法输入
→ 身份与权限校验
→ 识别业务上下文
→ 转换为统一来源内容
→ 对象匹配
→ AI 生成候选／摘要／回答／底稿
→ 展示来源、证据、缺失和影响
→ 用户人工确认
→ 服务端重新鉴权、校验、幂等
→ 调用正式业务接口
→ 返回正式对象
→ 审计、指标、失败降级
```

核心原则：

1. 外部材料、AI 推断和未确认候选都不是正式业务事实。
2. 0.1 所有正式业务写入均须人工确认；不存在低风险自动写入。
3. AI 不得绕过瑞赢权限、对象状态、必填规则和正式业务接口。
4. AI 不可用只降低效率，不能阻断销售活动、任务或日报的手工主链。
5. Coze 不得直接写正式 CRM 对象；所有写入必须经过瑞赢候选层和服务端校验。

## 2. 0.1 能力分层

### 2.1 核心上线阻断闭环

```text
沟通内容
→ 对象匹配
→ 候选销售活动＋候选任务
→ 证据与影响预览
→ 发起销售本人确认
→ 正式写入
→ 审计追溯
→ 失败可手工接管
```

任一关键节点不可用，均视为核心闭环未通过。

### 2.2 0.1 配套能力

日报底稿、客户／线索／商机对象摘要、对象内业务问答、轻量跨对象问答、知识检索、今日预计处理任务总结、主管关注摘要和会前准备摘要独立验收，不得替代核心闭环。M20 采用统一“拟写字段—人工修改确认—正式业务接口创建—逐条结果”架构；0.1 首批开放线索创建试点，客户、联系人、商机的助手创建沿用架构但不在 0.1 启用，四类对象的手工 H5 创建不受此试点范围限制。

### 2.3 输入范围

| 层级 | 输入 | 上线关系 |
|---|---|---|
| 核心阻断输入 | H5 文字、粘贴文本、当前用户有权的瑞赢正式对象 | 必须通过 |
| 0.1 正式增强输入 | 大圆在线文档、录音／语音、图片、文件 | 分项 POC 和开关启用；单项不可用不阻塞文字核心闭环 |
| 本期不进入 | 工作手机自动采集 | 无入口、接口、配置和验收 |

0.1 不建设周报、销售教练、赢率预测、外部情报、自主报价、自主承诺、自主对外发送或瑞赢自有 Agent Studio。

## 3. 端职责与页面

### 3.1 企业微信 H5

H5 是 0.1 的主要 Agent 操作端，承担当次输入、上下文选择、对象匹配、候选生成与确认、所有已开放候选类型的批量确认、正式写入、AI 待确认、摘要问答、知识检索、会前准备、今日任务总结、日报及主管关注摘要。M19 是全局唤起层，AI 首页、来源证据、候选历史和写入失败使用全屏二级页，不另占底部 Tab。

```text
瑞赢 H5
├─ AI 首页：今日预计处理任务／能力入口／待确认数量／最近结果
├─ 沟通整理：来源输入／上下文／对象匹配／生成结果
├─ 候选确认：销售活动／任务／试点线索／证据／修改／影响预览／单条或批量确认／忽略
├─ AI 待确认：当前待确认／历史待处理／写入失败
├─ 会议任务确认：来源／任务列表／批量选择／逐条执行结果
├─ M20 助手新增：目标对象／拟写字段／字段来源与确定性／查重／缺失／修改确认／正式记录 ID
├─ 对象 AI：摘要／问答／知识检索／会前准备
├─ 日报：首次生成共用草稿／销售编辑／提交；原始底稿仅 PC 查看
└─ 主管关注：团队摘要／关注事项／源对象入口
```

### 3.2 PC

PC 保持轻量，只提供 AI 数量／状态入口、团队 AI 处理情况、原有日报 PC 能力和 AI 运行记录；能力、来源、试点范围和预生成业务参数由 06 的单页四页签配置，Run ID、失败、重试和日志由 08 统一治理。0.1 不建设 PC 自由输入生成候选、完整候选编辑器或第二套完整 Agent 操作端。

H5、PC 共用同一候选、权限、状态、正式写入结果和审计链。

## 4. 主动触发与系统预生成

系统主动触发只保留今日预计处理任务总结、主管关注摘要、日报底稿三项：系统固定时间预生成，不主动推送；日报首次生成后不提供主动刷新或新增事实合并，其他摘要能力按各自规则展示数据截至时间。

沟通整理、会议纪要提炼、对象摘要、业务问答、知识检索和会前准备摘要均由用户主动发起。AI 不得基于模型自主判断并创造新的业务动作。

系统预生成使用受限独立服务身份，必须记录为谁生成、允许访问的数据范围及结果归属。

## 5. 统一来源内容与数据治理

```text
文字／粘贴 → 来源内容
录音 → 转写 → 来源内容
图片 → OCR／多模态识别 → 来源内容
文件 → 内容解析 → 来源内容
大圆在线文档 → 授权读取 → 来源内容
```

来源内容始终不等于正式业务事实。

1. 已在大圆、瑞赢或统一文件存储中的原件不在 Agent 重复复制；Agent 保存来源 ID、版本、类型和时间。
2. 手工输入或粘贴没有其他原件时，保存当次原始输入。
3. 录音、图片和文件统一进入文件存储，Agent 只保存文件 ID。
4. 保存当次实际用于生成的转写、OCR 或解析结果版本，以及候选使用的必要证据片段或定位信息。
5. 撤权后前台不继续展示无权原文；审计只保留最小必要元数据。

增强来源必须分别通过格式、大小、授权、解析、版本、定位、失败重试和降级 POC 后才能开启。

## 6. 业务上下文与对象匹配

### 6.1 上下文

- 从对象详情进入时自动带入当前对象作为主上下文，关联对象仅作参考。
- 从统一 AI 入口进入时，由用户选择对象，或由系统匹配后交用户确认。
- 上下文允许切换；原输入可以保留，但已生成候选立即失效并须重新生成。
- 正式写入前重新校验对象状态、版本和权限。

### 6.2 匹配

原则是“精确匹配优先，模糊匹配只推荐，歧义必须人工选择，无匹配不强绑”。

- 唯一标识优先精确匹配；名称、姓名等可模糊匹配。
- 单一可信结果可默认选中，但必须明确展示；多结果必须人工选择。
- 无匹配不得自动创建客户、联系人、线索或商机。
- 无权对象不得通过名称、数量、排序或摘要侧漏。
- 用户可人工改选，不要求填写理由；系统保存原推荐和最终选择。
- 前台不显示复杂置信度百分比，后台可保留匹配评分用于质量分析。

## 7. 候选销售活动

候选字段严格映射正式销售活动字段，不建立第二套业务模型，至少支持关联业务对象、活动时间、活动方式／类型、已有联系人或参与人、沟通内容／事实摘要、沟通结论及正式销售活动已有其他必填字段。

Agent 元数据单独保存：来源、来源版本、字段证据、事实／推断／缺失、AI 原建议、用户最终值、修改差异、模型／规则版本。

1. 联系人只关联已有联系人，不自动创建。
2. 无合法业务对象不能正式写入销售活动；客户未识别时应关联正式线索。
3. 一次沟通默认生成一条候选销售活动。
4. “下一步”优先转换为候选任务，不在销售活动中新增重复正式事实字段。
5. 候选销售活动不得直接写成正式拜访。

## 8. 候选任务与会议批量确认

候选任务字段沿用正式任务模型，包括标题、关联业务对象、来源销售活动、责任人、截止时间、任务类型和完成标准／说明。

1. 谁发起 Agent 提炼，谁确认候选；正式责任人可以是他人。
2. 向他人创建正式任务时，仍校验发起人是否具有相应指派权限；正式任务写入成功后直接待处理，不设置接收、拒绝、验收或退回。
3. 责任人无法判断时必须人工补齐；截止时间没有来源依据时不得由 AI 编造。
4. 候选允许暂缺正式任务必填字段，但缺失未补齐前不得写入。
5. 相似任务只提示，不自动合并；完全重复请求由幂等机制阻止。

一份会议纪要可生成零到多条候选任务，由发起会议提炼的人确认整批候选。所有已开放的候选类型均支持跨来源批量选择和确认，不新增正式任务负责人二次确认候选机制。每条候选可先单独修改；批量写入逐条执行权限、必填、查重、关联、版本、冲突及业务规则校验，允许部分成功并展示每条正式记录 ID 或失败原因。存在对象依赖时先写上游对象，上游失败的下游候选保持未写入并说明阻断原因；不作跨对象全局回滚。

## 9. 正式写入、幂等与重试

M20 创建类候选必须展示目标对象、拟写字段、每个字段的来源证据与事实／推断／缺失标记、相似或重名对象、正式必填缺口。用户可改选对象、修正字段或忽略；确认前不得产生正式 CRM 对象。确认后调用对应对象的正式创建接口，再次校验用户权限、对象关系、查重、必填、版本与幂等键，返回正式 ID 和逐条结果。0.1 线索试点沿用 02 模块的正式创建及查重规则；助手不能直接改变既有商机阶段或任务主状态。

活动和派生任务一起确认时：

```text
创建正式销售活动
→ 返回销售活动 ID
→ 逐条创建关联该销售活动的正式任务
```

不做跨对象全局回滚。活动创建失败时派生任务不得继续；活动成功后，成功任务保留，失败任务单独重试。

| 维度 | 状态 |
|---|---|
| 候选状态 | 待确认／已确认／已忽略／已失效 |
| 确认方式 | 直接确认／修改后确认／批量确认 |
| 写入状态 | 未写入／写入中／写入成功／写入失败 |

可以出现“候选已确认、写入失败”。写入失败时保留确认内容和人工修改，使用原幂等键重试；重试前重新鉴权并校验对象、版本和业务状态。原确认人可以重试；技术处理人员只能处理技术故障，不得修改业务内容或替销售重新确认。业务环境已变化时停止机械重试。

## 10. 候选生命周期、去重与冲突

候选主状态固定为待确认、已确认、已忽略、已失效。“修改后确认”是确认方式，不是状态。

- 长期未处理候选仍为待确认，仅从默认列表进入“历史待处理”；时间作为业务参数配置。
- 用户主动不采用时为已忽略。
- 上下文切换、来源更新／删除、用户撤权、对象失效或状态已不允许写入时为已失效。
- 来源变化不得原地覆盖：旧候选失效，基于最新来源生成新候选。
- 技术重复强制幂等；业务相似只提示，不自动阻断或合并。
- 多来源指向同一事实时不自动合并候选，仅提示相关来源或相似候选。
- 证据冲突时并列展示，AI 不得裁决；用户选择最终值和采用来源，不强制填写理由。

## 11. 日报底稿与配套能力

### 11.1 日报底稿

日报使用独立版本模型，不进入通用候选状态机：

```text
首次 AI 原始底稿 → 当前工作草稿 → 正式提交版本
```

系统固定时间预生成或首次打开兜底生成，仅使用当时已确认的正式事实，生成一份含事实描述和 AI 总结的分段可编辑正文，PC 与 H5 共用。首次 AI 原始底稿保留且仅 PC 可查看。0.1 不提供新增事实提示、主动刷新、差异对比或草稿合并；已有销售编辑不被系统覆盖。无正式事实时由销售手工填写非空说明；未确认候选不得进入正式事实。提交时冻结最终正文、当时事实快照和来源，提交后不受后续 AI 结果影响。销售修改日报文字不回写源业务对象。

### 11.2 对象摘要、问答和知识

- 0.1 对象摘要优先支持线索、客户、商机，展示当前状态、最近关键活动、已确认需求／关注点／异议／风险、未完成任务、数据缺失、AI 总结、数据截至时间和来源。
- 对象内问答围绕当前对象及合法关联对象；轻量跨对象问答仅限当前用户权限内业务查询，不扩展为通用 BI。
- 无证据时统一回答“根据当前可访问的数据暂无法确认”。
- 知识检索只使用已发布且用户有权知识，显示文档、版本或更新时间；知识与业务事实分开标识。文档停用后不进入新回答，历史回答不自动改写。
- 会前准备摘要由用户主动触发。

### 11.3 今日任务总结与主管关注摘要

今日任务总结早上预生成，底单来自今日到期、已逾期、今日拜访、待确认事项及其他既有确定性规则；AI 只总结、归纳和解释，不生成新的正式任务或第二套任务优先级。

主管关注摘要早上预生成，底单只来自逾期任务、长时间无跟进、明确承诺未完成、商机缺少下一步、应交未交日报和关键数据缺失等确定性事实。不得给销售评分、形成绩效评价、自主判断人员优劣或自动为下属创建任务。

## 12. 权限、撤权和运维隔离

用户主动调用的有效能力取“当前用户三角色业务权限 ∩ Agent 服务身份能力”。Agent 不能成为权限旁路。

候选未确认前撤权时，不再展示无权原文、不允许确认、候选失效，只保留最小审计元数据。正式写入后撤权时完全回归原业务模块权限，不因对象由 AI 辅助创建而保留额外访问权。

主管可查看团队候选处理统计和自己原本有权的业务正文，但不能代销售确认，也不能因 AI 管理权限获得额外客户、沟通材料或原件权限。

AI 运行页面展示 Run ID、能力类型、状态、时间、模型／规则版本、来源类型、耗时、错误码、重试次数和写入结果；管理员（运营）按全部业务数据范围及页面/按钮权限查看相关业务内容。外部来源内容仍须满足来源授权，系统凭证不得明文展示。

## 13. AI 运行、审计与指标

每次运行生成唯一 Run ID，至少记录主动／系统触发、发起用户或生成对象、能力类型、来源类型／ID／版本、关联对象、开始／完成时间、模型／规则版本、状态、耗时、错误码、候选 ID、用户修改／确认／忽略结果、正式对象 ID、写入状态、重试次数和失败原因。

业务审计与技术运行日志逻辑分离，并可通过 Run ID、候选 ID 和正式对象 ID 串联。

试点优先统计对象一次匹配正确率、候选直接确认率、修改后确认率、忽略率、责任人改选率、正式写入成功率、手工降级率、可追溯率、平均处理时间及相较原人工流程的节省时间。先建立真实基线，不提前设置虚高阈值，不作为销售绩效。

### 13.1 试点质量指标口径

| 指标 | 计算口径 | 说明 |
|---|---|---|
| 提取准确率 | 与人工确认后最终值一致的关键字段数 ÷ 纳入评估的关键字段数 | 按字段评估，修改后确认可以保留其中正确字段；按候选类型分别统计 |
| 候选直接确认率／修改后确认率 | 各确认方式数 ÷ 已处理候选数 | 确认方式不是候选状态 |
| 候选忽略率 | 已忽略候选数 ÷ 已处理候选数 | 不强制用户填写原因 |
| 对象一次匹配正确率／对象改选率／责任人改选率 | 按匹配和最终选择差异计算 | 评估匹配与结构化质量 |
| 写入成功率 | 成功写入正式记录候选数 ÷ 发起写入候选数 | 技术质量指标 |
| 手工降级完成率 | Agent 失败后通过手工路径完成的流程数 ÷ Agent 失败流程数 | 验证 Agent 不可用时闭环仍成立 |

指标阈值在试点前确定，0.1 先保证埋点、计算和下钻能力，不在无样本时虚设通过值。

## 14. 失败降级

AI 失败只能降低效率，不能阻断原业务。页面支持重新生成、保留输入、改用文字继续、手工记录销售活动、手工创建任务和手工填写日报。

技术性瞬时异常可有限自动重试。对象歧义、权限不足、必填缺失、来源冲突和责任人失效属于业务异常，不得自动重试。

## 15. Coze 与配置边界

| 责任方 | 职责 |
|---|---|
| Coze 私有化 | 模型、Prompt、Agent／Workflow、知识检索流程、AI 工具编排 |
| 瑞赢 | H5／PC 交互、鉴权、数据权限、上下文、候选、人工确认、正式写入、幂等、重试、审计、能力开关、试点范围、来源配置和预生成调度 |
| 01～04 模块 | 正式字段、必填规则、状态机、对象权限和正式业务规则 |

原则是“Coze 决定怎么生成，瑞赢决定能看什么、能做什么、能不能写”。

瑞赢业务管理员只配置 AI 能力／来源启停、试点组织／人员、三项预生成时间和历史待处理时间。Coze／AI 技术侧维护模型、Prompt、Workflow、AI 工具及知识检索实现；技术系统侧维护超时、自动重试、日志期限和服务地址。任何配置不得覆盖业务状态机、权限和正式必填规则。

## 16. 上线准入与阻断条件

上线前必须满足：文字输入核心闭环完整；对象匹配、确认和正式写入可追溯；不存在 Agent 权限旁路；正式写入全部人工确认；幂等阻止重复正式对象；部分失败可准确展示并安全重试；Coze 不可用时手工主链完整；真实试点可建立采用、改选和处理耗时基线。

以下任一情况阻断上线：越权读取或信息侧漏、未经人工确认写入、重复点击产生重复对象、写入失败显示成功、无法追溯来源和确认人、AI 故障阻断手工业务、核心沟通整理链路无法闭环。

## 17. 技术 POC

技术评审须完成以下 POC，但实现方案不得改变产品边界：Coze 私有化；大圆接入；录音转写；图片识别；文件解析；对象匹配；销售活动和任务结构化生成；权限内相似任务检测；来源版本与候选失效；正式写入与幂等；三项系统预生成；权限与撤权；Run ID 到正式对象 ID 的审计串联。
